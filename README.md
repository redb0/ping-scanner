# Ping Scanner

[![CI](https://github.com/redb0/ping-scanner/actions/workflows/ci.yml/badge.svg)](https://github.com/redb0/ping-scanner/actions/workflows/ci.yml)

CLI, который берёт набор веб-целей, делает по каждой HTTP пробу и показывает
статус по каждой из них.

Сейчас это **фаза 1**: последовательный прогон из аргументов командной строки.

**Фаза 2** — веб-сервис на том же ядре (`docs/adr/0001-reusable-core.md`).

## Возможности

То, что уже работает:

- голый домен нормализуется в `https://…`; `http` и `https` URL остаются как есть
- дубликаты после нормализации отбрасываются, порядок ввода сохраняется
- невалидные цели по умолчанию пропускаются
- `--fail-fast` останавливается на первом мусоре
- HTTP GET, редиректы, тело не скачивается, User-Agent `probe/1.0`
- Up — финальный статус `< 500` (4xx тоже Up); Down — 5xx или нет ответа
- для сетевых сбоев печатается reason: `timeout`, `DNS: …`,
  `connection refused`, `TLS: …`
- жёсткий таймаут клиента 5s, без флага на цель

Ещё нет: ввод из файла, параллелизм, `--timeout`, `--json`, цветная таблица,
SIGINT.

## Требования

- Go, версия из `backend/go.mod` (сейчас 1.25.11)
- для локального линта — [golangci-lint](https://golangci-lint.run/) v2.4.0
  и [just](https://github.com/casey/just), если пользуетесь `justfile`

## Установка

```bash
git clone git@github.com:redb0/ping-scanner.git
cd ping-scanner/backend
go build -o ping-scanner ./cmd/cli
```

Отдельного релиза и `go install` пока нет.

## Использование

```bash
./ping-scanner example.com https://x.io
```

Пример строки:

```text
https://example.com Up 200
https://x.io Down 0 timeout
```

Невалидный аргумент без `--fail-fast` не валит весь прогон:

```bash
./ping-scanner example.com ftp://x.io
# stderr: skipped 1 invalid target(s)
```

## Флаги

| Флаг          | Значение по умолчанию | Что делает                                     |
| ------------- | --------------------- | ---------------------------------------------- |
| `--fail-fast` | выкл.                 | останавливается на первом невалидном аргументе |

Флаги лучше ставить до позиционных аргументов: стандартный `flag` в Go
перестаёт их разбирать после первого не-флага.

## Формат вывода

Одна строка на Target, в порядке аргументов:

```text
<target> <Up|Down> <status> [reason]
```

`status` — финальный HTTP-код после редиректов, либо `0`, если ответа не было.
`reason` только у Down с сетевой ошибкой; у 5xx колонка пустая.

## Коды завершения

| Код | Когда                                                                      |
| --- | -------------------------------------------------------------------------- |
| 0   | все проверенные цели Up                                                    |
| 1   | хотя бы одна Down                                                          |
| 2   | нет целей после парсинга, `--fail-fast` на невалидном входе, ошибка флагов |

Пропуск невалидных сам по себе код не меняет. Если после skip ничего не
осталось — это уже «нет целей», код 2.

## Как это устроено

Probe — один GET. Scan — проход по всему набору, сейчас строго по очереди.
Классификация Up/Down, таймаут и exit-код живут в `backend/internal/probe`.
CLI только парсит флаги, печатает строки. Так задумано в ADR-0001: следующий
транспорт (HTTP API) не должен заново собирать эти правила.

## Планы

Из spec фазы 1, ещё не в коде:

1. `-f` — цели из файла
2. `--concurrency` (дефолт 10), вывод в порядке ввода
3. `--timeout` на цель (дефолт 5s)
4. Ctrl-C: отмена висящих проб, частичный результат
5. таблица, цвет в TTY, `--json`, сводка `N up, M down, T total`

Потом фаза 2: веб-сервис поверх того же `internal/probe`.
